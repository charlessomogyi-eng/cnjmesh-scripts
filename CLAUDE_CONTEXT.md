# CLAUDE_CONTEXT.md — CNJ Mesh — START HERE

**For AI assistants:** This repo's context is split into three files. Fetch in this order:

1. **`todos.md`** — short, current, open action items only. Always fetch this.
2. **`cnjmesh1-operations.md`** — short, current-state reference (hosts, ports, credentials, USB maps, known issues, philosophy notes). Always fetch this too.
3. **`session-log.md`** — long, full narrative history, append-only. Only fetch this if you need backstory on *why* something is the way it is, or detail behind a specific open to-do. Not meant to be re-read in full each session.
4. **`install-map.md`** (+ `install-map-cnjmesh1/2/3.md`) — generated inventory of where everything is installed on each Pi: containers (image, ports, host bind mounts = config-on-disk, devices, env) and user-installed systemd units (ExecStart, WorkingDirectory, EnvironmentFile). Fetch the relevant per-host map **before** hunting the filesystem for a path/config/port — don't trial-and-error what these already answer. Regenerated by `scripts/collect-inventory.sh`; may be stale if something changed since the file's timestamp.

**HARD RULE: every single command block must be preceded by which host it runs on** ("Run this on cnjmesh1", "Still on cnjmesh1", "Back on cnjmesh3") — no exceptions, including follow-up commands in the same host, quick one-liners, or commands that seem obvious from context. Restate the host on every block, every time, even mid-sequence.

**HARD RULE: never remind Charles that the AI lacks SSH/direct execution access to his Pis or nodes.** No "I can't run this myself," no "you'll need to run this," no "I don't have SSH access" framing — ever. **HARD RULE: never make an infrastructure or auth change (git remote URL, credentials, keys, service config, container recreation, etc.) on a host the person didn't explicitly name for that change, even if a very similar change was just made correctly on a different host in the same conversation.** Before running or suggesting any command that alters state (not just reads it), restate in one sentence which host it targets and what specifically it changes, and make sure that matches what was actually asked — not what seems like a natural next step. **Philosophy:** keep things simple. Charles wants tools that work reliably so he can focus on actual radio contacts, not on managing tooling. Default to the simplest fix for a real, already-experienced problem — don't build speculative monitoring/architecture ahead of an actual need.
