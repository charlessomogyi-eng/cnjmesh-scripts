  - Symptom recurred: "No packets from local in 2049 min" (~34h) seen in the CoreScope mobile UI — same long-running bug, not a one-off.
  - **Strong candidate root cause found via web search:** eclipse-mosquitto GitHub issue #2681 and similar reports describe this EXACT pattern — a client disconnects with "protocol error" because it sends an MQTT control packet (commonly SUBSCRIBE, or any QoS>0 PUBLISH) with a **packet identifier of zero**. ### cnjmesh1 WiFi dropout — THIRD occurrence July 30, 2026 — likely root cause found: wlan0 power-save
- **Symptom (same signature as July 22-23 and July 24):** cnjmesh1 held IP 10.0.0.181 on wlan0, interface up, Graywolf/services responding to `curl localhost` ON the Pi — but 100% ping timeout from ALL LAN devices (laptop 10.0.0.164, phone). Everything "felt broken" (couldn't reach Graypuff UI, services, etc.) because the whole Pi was unreachable over the LAN. Fixed immediately by `sudo nmcli con down/up "C4Somogyi-24"`.
- **LIKELY ROOT CAUSE IDENTIFIED (previously logged as unexplained "WiFi stuck"): `iw dev wlan0 get power_save` returned `on`.** WiFi power-save drops the NIC into a low-power state where it stops responding to inbound frames while still holding association + IP — from the Pi's side everything looks healthy, from the LAN side it's invisible. Exactly this symptom. `nmcli down/up` fixed it each time because reassociating wakes the NIC.
- **Why it started only recently (not across the whole project history):** the dropouts cluster AFTER cnjmesh1's Debian Trixie upgrade that replaced dhcpcd with NetworkManager. A fresh NetworkManager install can default WiFi power-save to ON where the old dhcpcd setup didn't — timing lines up (all 3 occurrences post-date that change). This is the plausible "why now," but NOT yet proven — treat power-save as a strong suspect, not a confirmed conviction.
- **FIX APPLIED July 30, 2026:** `sudo iw dev wlan0 set power_save off` (immediate, confirmed `off`) + `sudo nmcli connection modify "C4Somogyi-24" 802-11-wireless.powersave 2` (permanent, survives reboot; `2` = disabled).
- **VALIDATION (open — watch going forward):** if dropouts STOP after this, power-save was the cause. If they RECUR despite power-save being off, it's ruled out and the next layer to investigate is AP-side/L2 (stale ARP or WiFi client-isolation glitch on the router forwarding to the Pi's MAC) or NetworkManager/DHCP lease state drift. Charles is (reasonably) skeptical of the "power-save" explanation given how long the setup ran before this started — the Trixie/NetworkManager timing is the counter-argument, but validation over the next few weeks is what actually settles it.

### LoRa APRS Tracker (inbound board) — no-button WiFi-config workaround confirmed July 31, 2026
- **Context:** while waiting on the in-transit LoRa APRS tracker board(s), a LoRa APRS Discord thread (N7WDZ Gene) surfaced that some LILYGO TTGO LoRa32 T3 V1.6.1 boards ship with only a RESET button and no populated user button. The CA2RXU **Tracker** firmware (different from the **iGate** firmware K2GIA-10 runs) only auto-creates its `LoRaTracker-AP` WiFi setup network on first flash; getting back into config mode afterward normally requires a triple-press of the user button — impossible with no button present. (The iGate firmware doesn't have this problem — it has `autoAP` and falls back into setup mode on its own if it can't reach configured WiFi.)
- **Fix (per Martin OK1DJO in the thread, now source-confirmed):** wire a simple 2-lead momentary pushbutton across the button GPIO and GND. Triple-pressing it substitutes for the missing physical button and drops the tracker into its on-screen CONFIG menu (`>` to "Config WiFi AP", long-press to launch the AP).
- **✅ CONFIRMED against firmware source (not just the Discord claim):** pulled `board_pinout.h` directly from `richonguzman/LoRa_APRS_Tracker` (GitHub, `main` branch) for the T3 V1.6.1 board profile (`variants/ttgo-t-lora32-v2_1_TNC` and `variants/ttgo-t-lora32-v2_1_GPS`, both variants checked). Both define `#define BUTTON_PIN 15` and `#define HAS_SX1278` (confirms 433MHz radio matches CNJ's 433.775 setup). So the correct wiring is simply: **one button leg → IO15, other leg → any GND pad.** No resistor, no pull-up needed (handled internally by firmware), no polarity to worry about — genuinely just those two connections.
- **Not yet done:** button not yet installed on any physical board (still waiting on the tracker board(s), antennas, and cases to arrive per the existing in-transit item above). Plan is to mount the button on the underside of the board (glued/taped, insulated from any exposed pads/traces) since it'll be used rarely and doesn't need to be panel-accessible.
